2. 🗄️ Relational Database Schema Design (ERD Explanation)
To systematically operate a multi-tenant environment accommodating both Kirana Wholesalers (Inventory tracking + Open ledger debt) and Salons (Timed appointment reservations + Variable technician margins), the database architecture leverages Single-Table Extensibility paired with Polymorphic Event Relations.
📐 Entity-Relationship Logic & Architectural Foundations
Shops (The Tenant Root Node): The primary structural anchor. Every entry inside the infrastructure contains a foreign reference mapping back to this table. The critical discriminator attribute business_type ('wholesale' or 'salon') dictates how client-side data structures parse and render the application UI layout dynamically.
Users (Staff / Access Identity Profiles): Maps authorization access control groups (roles like owner, billing_clerk, salon_stylist). For service verticals, this identity entity manages dynamic commission configurations used in daily payout calculations.
Customers (The Consolidated Account Ledger): A cross-functional entity tracking dual identities. When processing under a wholesale scope, the system targets the current_due and credit_limit properties to throttle checkout permissions. Under a salon context, the application reads the loyalty_points register to calculate rewards.
Products & Services (The Unified Catalog Matrix): Merges raw retail physical stock and abstract billable labor onto a uniform index. An evaluation check over the is_service boolean flag tells the internal inventory engine whether to bypass row-locking routines during checkout validation loops.
Invoices & Invoice_Items (The Immutable Operational History): Tracks the direct details of processing events. These two tables operate independently from the live entity tables (products, customers), ensuring that transactional housekeeping runs without breaking existing historical totals.

4. 🔏 Data Purging Logic (Database Archiving Without Discrepancies)
The Architectural Core: The platform decouples transaction records from balance state machines. When cashiers finalize an order, calculation routines run once to update the true states inside products.stock_quantity and customers.current_due.
The underlying historical documents (invoices and invoice_items) serve exclusively as immutable audit receipts and visualization models.
When a shop owner executes a database cleanup routine to drop thousands of past line items, the system removes records down the line from the invoices reference using a cascading delete tool (ON DELETE CASCADE).
Because the parent parameters (current_due and stock_quantity) are isolated from historical changes or use safe fallback pointers (ON DELETE SET NULL), current ledger records experience 0% systemic distortion. Database sizes are minimized, response performance stays optimized, and open balances remain unchanged.
5. ⚡ Real-Time Multi-Counter Synchronization Logic
To ensure concurrent checkout actions on the same item index do not introduce racing state overlaps or inventory discrepancies across terminal connections (e.g., GF and FF lanes), the platform combines Supabase Realtime Broadcast Sockets with strict PostgreSQL Isolation Row Locks.
A) Live State Updates (Next.js Client Components)
The system attaches a real-time reactive event wrapper on checkout terminal connections to catch modifications to your database without using expensive browser reload loops:
typescript
import { useEffect, useState } from 'react';
import { supabase } from '@/lib/supabaseClient';
export default function BillingCounter({ shopId }) {
  const [products, setProducts] = useState([]);
  useEffect(() => {
    // 1. Initialize local cache from master product list state
    fetchProducts();
    // 2. Subscribe to transactional mutation broad-streams inside the target tenant boundaries
    const stockChannel = supabase
      .channel('live-stock-changes')
      .on(
        'postgres_changes',
        { event: 'UPDATE', schema: 'public', table: 'products', filter: `shop_id=eq.${shopId}` },
        (payload) => {
          // Captures state mutation events from any transaction stream and updates the counter view within < 1 second
          setProducts((prevItems) =>
            prevItems.map((item) => (item.id === payload.new.id ? { ...item, stock_quantity: payload.new.stock_quantity } : item))
          );
        }
      )
      .subscribe();
    return () => {
      supabase.removeChannel(stockChannel);
    };
  }, [shopId]);
  return (
    <div>{/* The high-speed billing interface component parses and renders here */}</div>
  );
}

B) Preventing Stock Double-Selling Collisions (Row Locking Framework)
When parallel terminals process execution signals down to the microsecond on the last available item lot, the backend engine processes the operation safely by invoking a protected database storage routine:
sql
CREATE OR REPLACE FUNCTION secure_billing_deduct(target_product_id UUID, req_qty NUMERIC)
RETURNS BOOLEAN AS $$
DECLARE
    current_stock NUMERIC;
BEGIN
    -- 🔒 ROW LOCK INVOCATION: Isolate the matched record line from any alternative processing threads until transaction closes
    SELECT stock_quantity INTO current_stock 
    FROM products 
    WHERE id = target_product_id FOR UPDATE;
    -- Evaluate absolute quantity constraints against requested inventory amounts
    IF current_stock >= req_qty THEN
        UPDATE products 
        SET stock_quantity = stock_quantity - req_qty 
        WHERE id = target_product_id;
        RETURN TRUE; -- Success conditions met, row constraints unlock and commit safely
    ELSE
        RETURN FALSE; -- Insufficient inventory state exception flagged, modifications roll back cleanly
    END IF;
END;
$$ LANGUAGE plpgsql;
